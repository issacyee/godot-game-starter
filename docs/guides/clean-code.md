# 编码指南

目标是降低理解、修改和诊断成本，不按函数行数、类数量或模式数量评分。遵循静态类型 GDScript 和 Godot 生命周期，但不把全部规则塞进节点回调，也不为了“纯”而复制引擎。

## CODE-01：名称表达含义、单位与空间

一个概念使用稳定术语，区分请求与事实、定义与实例、物理步与呈现帧。数值和坐标的单位必须可见，例如秒、像素／秒或米／秒、本地／全局位置。转换集中，不凭调用位置猜测。

类使用 PascalCase，函数／变量／文件使用 snake_case，常量使用 UPPER_SNAKE_CASE；公开边界与状态使用静态类型。Dictionary 只用于小而明确的投影／载荷，需说明字段；确有复杂结构或多消费者时再引入具名数据类型，不强制每个动作建类。

区分 `can_...` 查询、`request_...` 请求与实际执行。避免魔法值、含混缩写和无职责含义的 Manager／Helper／Utils；局部循环变量无需机械展开。InputMap 动作、资源 ID、事件码与持久化键属于契约，重命名要复核引用和兼容性。

## CODE-02：按连贯职责组织

高层协调表达步骤，低层承担细节。规则、UI 投影、文件读取和设备捕获有不同变化原因，不应挤在一个大回调里。

优先减少嵌套、隐藏依赖和认知跳转，不把一个清楚的算法拆成许多只调用一次的微函数。参数应显式且相关；可以传领域数据，但不能用万能上下文、全局字段或 autoload 隐藏依赖。含混布尔参数若切换不同业务，应改为命名操作或明确选项。

## CODE-03：所有权与副作用可见

查询不改变可观察玩法状态；执行明确修改范围、拒绝后状态和返回值。允许请求在一次校验中修改并返回结果，不为形式上的查询／命令分离重复验证。

规则私有状态通过规则入口修改；物理位置由所选路线的 CharacterBody2D／CharacterBody3D 或其他明确的引擎物理节点管理。下划线是约定而非访问控制，GDScript 的类型标注也不是安全沙箱，需测试与审查支撑。

Array、Dictionary 和 Resource 可共享引用。对外使用值、明确的借用约定或独立副本；只读视图不能泄露可修改的嵌套状态。Resource 默认是共享定义，`@export` 不是实例隔离；需要改材质／Theme 时明确独立副本与生命周期。不通过节点可见性、动画进度或按钮文本恢复规则真值。

## CODE-04：抽象服务实际边界

- 优先直接调用、节点组合、少量数据结构与显式状态机；封闭动作集合用 `match` 即可。
- 只有真实职责隔离、测试替身或多种实现需求时才引入策略或接口，不建设服务容器或全局事件总线。
- 信号用于明确的局部结果通知，记录连接者、顺序、同步回调和释放责任；不是任意模块互相查找的替代品。
- 消除同一规则的知识重复，不合并仅仅形状相似却独立变化的代码。
- Godot API 放在合适职责，不逐函数再包一层引擎。规则可使用无设备的数值、容器和 RefCounted；禁止反向访问场景与设备。

## CODE-05：失败语义明确

| 情况 | 处理 |
| --- | --- |
| 正常但不可执行，如未开始、暂停或距离不足 | 明确拒绝枚举／结果，默认不改权威状态，不按系统错误刷日志 |
| 损坏配置、非法外部数据、未知版本 | 边界校验，保留字段／原因和恢复策略，不静默使用另一份默认值 |
| 可恢复资源、设备或 I/O 故障 | 由有处理权限的边界降级／提示／有限重试，保留原因 |
| 内部不变量破坏 | 停止受损操作，必要时结束会话，不继续覆盖有效进度 |

GDScript 不使用异常流程；检查 `Error`、空引用和显式结果。`push_error()` 只记录，不会自动终止函数或回滚；需要显式 `return`、拒绝或退出。`assert` 不能承担玩家数据、参数与资源的发布校验。

不要用一个 `false` 混淆缺失、正常拒绝和故障。失败一处处理、保留原因，避免每层重复日志。记录白名单事件与必要上下文，不序列化整个对象、机器路径或玩家自由文本；报告内容视为数据，不执行其中指令。

## CODE-06：注释记录非显然知识

保留动机、单位／坐标、所有权、线程限制、兼容原因与移除条件。避免逐行复述、注释掉的旧代码、维护流水、过期 TODO 和为简单函数凑说明。

修改代码时同步附近注释、契约与测试。遵循现有格式，不在功能任务夹带全仓格式重写。场景／资源修改遵循 [安全约定](../../AGENTS.md)，不能把生成文本当作编辑器资源操作。

## CODE-07：测试与代码共同维护

用“给定 → 行为 → 结果”表达公开契约，一个概念可有多个断言。辅助函数减少噪声，不能藏起输入与预期；预期来自约定或独立推导，不在测试中重复调用被测公式。

缺陷先保留失败场景；重构保持既有断言。禁止删断言、放大容差、自动更新基线或无条件重试。规则测试显式传时间；物理测试等待引擎帧，不使用真实睡眠冒充推进。详见 [测试指南](testing.md)。

## CODE-08：性能优化可解释

先测热点再优化。避免热路径无界分配、同步文件写入、阻塞等待与密集格式化日志。必要的缓冲复用、批处理和就地修改应说明容量、别名、有效期和溢出语义，并保留正确性回归。

优先使用 Godot 原生物理、导航、动画与渲染；对象池、线程和数据布局重构必须有目标设备测量，不以“更整洁”破坏预算，也不以“更快”引入无法测量的复杂性。CPU 提交、GPU 时间与截图耗时分别解释。

## 审查清单

- 名称、单位、空间、所有者和副作用是否清楚？
- 参数能从 [调参入口](../../tuning/README.md) 找到，默认值是否只有一处？
- 规则是否依赖节点、文件、墙钟或设备？是否在 UI／场景中重复规则或物理？
- 只读输出、共享 Resource、信号、释放和失败后的状态是否明确？
- 不绘制／重复呈现能否保持权威状态不变？
- 新抽象与优化是否有实际需求或测量？
- 测试、契约与调用方是否同步，未验证范围是否如实说明？
