# 从零构建游戏

本文是启动顺序和阶段闸门，不是要求所有游戏实现全部能力。新项目按阶段推进，已有项目可用它盘点差距；同阶段可按需求调整，跳过项说明理由。通用边界见 [架构](guides/game-architecture.md)，日常协作见 [工作流](workflow.md)。

## 阶段 0：项目身份与简报

复制或克隆独立项目，不携带缓存、产物或玩家数据。按 [模板定制](CUSTOMIZATION.md) 修改应用名和用户目录，配置引擎与按需开发依赖。默认一个仓库就是一个游戏，直接维护自己的源码、工具与文档。

将 [BRIEF](BRIEF.md) 写成真实游戏目标，至少回答：

- 核心循环、成功／失败条件、一次游玩的入口与出口；
- 内容规模、目标平台和输入设备、明确范围外内容；
- 玩法与表现的权威状态、引擎承担什么、哪些规则单独测试；
- 当前未决项，重要选型的理由、替代方案和代价。

**闸门**：意图与范围已确认，能描述最小可玩的完整路径；本地路径不进入共享配置。

## 阶段 1：选择能力与边界

复核 [CAPABILITIES](CAPABILITIES.md)，对需要的能力写清已包含、计划实现、按需后置或禁用及理由。启用、实现、测试和目标设备通过是不同状态。模板仅提供 Windows 自动化路径，不预设每个游戏都支持其他平台。

按 [契约模板](contracts/module-template.md) 为关键跨模块语义确定所有者、请求／结果／事件、参数时机和验证。默认使用节点组合、直接调用、InputMap、Resource 和 GdUnit4，不先搭通用框架。

**闸门**：启用能力有使用者、入口和验证计划；未启用项没有假接口；没有两个模块同时拥有同一真值。

## 阶段 2：最小纵向可玩切片

1. 在 RefCounted 规则中定义关键不变量与拒绝，先测正常、边界、非法输入和重置。
2. 协调层将玩家、UI、AI 或测试输入转换成语义请求，返回明确结果；连续移动由物理节点和 InputMap 接入。
3. 用 Godot 场景建立物理世界和最小 UI。引擎负责碰撞、时间调度、资源导入与绘制，规则不另存坐标或模拟碰撞。
4. 明确标题、运行、暂停、继续、重开和退出；失焦／最小化／休眠策略另选，不能由手动暂停推导。

**闸门**：实际场景可完成进入 → 操作 → 状态结果 → 暂停／继续 → 重开／退出；反复重开不累积旧实例或信号。新进程重载验证 owner、资源、信号与物理，规则可无窗口测试。

## 阶段 3：表现、参数与内容

表现从规则值视图或已发生事实更新 UI、可见性、动画、镜头和音效。重复呈现、关闭反馈不改变规则；交互反馈只能在请求成功后发生。视觉状态可重建，不靠它反推是否已经成功。

设计参数从 [tuning](../tuning/README.md) 统一发现，先完整校验再按职责投影。共享 Resource 不存运行状态；默认启动冻结，重开沿用。使用实验预设比较，去掉预设恢复基线，不隐式加载本地覆盖。

字体默认使用 Godot 内置回退，文本整形与布局交给 TextServer 和 Control/Container；有明确字形需求再添加经许可的字体。音频、动画、粒子、导航与多语言只在启用时接入原生节点和对应故障路径。

**闸门**：场景状态与可见反馈一致；重复呈现不修改权威状态；参数实际生效且不污染基线；目标视口、字号和设备上的裁切、缺字与输入需实际验证。

## 阶段 4：按需持久化

没有保存需求就跳过实现。启用时先定义“继续玩”要恢复什么：规则、引擎物理状态、计时、进行中动作、顺序和随机进度等；只保存坐标不自动足够，诊断快照也不是存档。

玩家设置与进度分开；定义版本、校验、原子写入、失败可见和旧有效数据保留策略。参数变更时明确采用当前参数、归档参数还是拒绝，不混用。

**闸门**：重启恢复通过；不中断分支与中途恢复分支逐步比较，并保留删除关键字段会失败的反例。存储失败、损坏和版本不兼容不静默清零；全部在一次性位置验证，不碰玩家数据。不承诺 Godot 物理跨平台位级一致。

## 阶段 5：诊断、技术视觉与性能

从第一条纵向切片保留必要的有界诊断，记录稳定动作码、结果和有效参数，不等到发布才排错。新增持久日志、玩家报告、崩溃留存或上传需单独设计；模板的内存轨迹不是完整回放。

技术视觉验证使用实际包的图像和同帧状态，检测相关元素、位置、可见反馈及必要的连续帧。性能另在目标设备使用 Godot profiler／监视器和明确预算测量；截图编码、无头耗时不代表 GPU 帧预算。

**闸门**：可定位构建与参数；容量和失败语义明确且不泄露隐私；技术视觉有客观判据；仅对已测场景／设备声明性能。审美、趣味和主观手感作为独立反馈，不用于自动打分。

## 阶段 6：目标产物与交付

按 [README](../README.md) 运行 `test`、`negative`、`export`，再 `verify` 完整目录。替换玩法时同步改 [定制入口](CUSTOMIZATION.md) 列出的产品输入、状态、像素判据；模板默认脚本只证明示例，不证明新游戏。

**闸门**：当前源码与有效参数对应实际产物；目标平台的真实输入完成核心路径；许可完整；必需故障能被拒绝。CI、无头测试、真实设备、技术视觉和性能分别说明范围，缺证据如实报告。

模板只生成未签名 dev 包。正式发布还需实际版本、完整源码身份、符号与许可归档、签名／分发流程、目标设备矩阵和故障恢复决定，不能把 dev 绿灯等同正式发行。

## 每阶段通用检查

- 规则不依赖场景、设备、文件或墙钟；GDScript 测试仍运行于 Godot。
- 规则、协调、物理、表现各自所有权清楚；表现缓存和 Resource 不成为第二份真值。
- 改规则复核请求、规则、事实、快照影响、测试五处；不为未启用能力新增机制。
- 实际验证从快到慢，自动化隔离用户目录，报告不覆盖或复用；工作记录不写进共享指南。
- 不为符合模式名称重写清晰实现。偏离默认接法时先说明需求、替代方案、代价和验证。
